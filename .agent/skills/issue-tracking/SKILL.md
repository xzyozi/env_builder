# 課題管理

## 概要

作業の「やること」「判断待ち」「状態」を、project の `docs/issues/` に残す手順。
規約の本体は `.agent/rules/issue-tracking.md`。ここでは、その規約を再現する操作の順序を示す。
課題の実体は Git 管理外の project 側にあり、このスキルは実体を作らない。

## 準備

1. project ID を確定する（依頼文または `--project`）。推測しない。
2. 課題ディレクトリを決める。既定は `<project-root>/<project-id>/docs/issues/`。
   `<project-root>` は環境変数 `ENVB_PROJECT_ROOT`、未設定ならリポジトリ直下の `projects/`。
3. 既に `docs/<phase>/issues/` のような階層がある project は、作業に対応するフェーズのディレクトリを使う。
   どれか判断できなければ、利用者に尋ねる。
4. `.agent/rules/issue-tracking.md` を読む（状態の定義と更新の規則）。

## 作業の開始時

1. 対象ディレクトリの `INDEX.md` を読む。
2. 次を把握して、利用者に 3 行程度で伝える。
   - `in-progress` と `blocked` の課題
   - 「未決事項」の表で未回答のもの
3. 今回の作業に対応する課題があれば、その課題ファイルを読む。
   無ければ「起票」へ進む。課題の状態が `open` なら、着手した時点で `in-progress` にする（「状態の更新」）。

## 起票

1. ID を決める。`INDEX.md` の既存 ID と重複させない。接頭辞と採番は project の既存の流儀に合わせる。
   既存が無ければ `001` から連番にする。
2. ファイル名は `<ID>-<slug>.md`。slug は英小文字・数字・ハイフンだけにする。
3. `.agent/templates/issue.md` を元に、課題ファイルを編集ツールで作る。
   - 状態は `open`。目的、確認済みの事実、やること、完了条件を埋める。
   - 完了条件は、確認できる形で書く。
   - IP、パスワード、トークン、鍵の内容を書かない。接続先は `inventory/servers.json` のキーで書く。
4. 同じ作業の中で `INDEX.md` の表に 1 行追加する。
5. `INDEX.md` が無い project は、先に `.agent/templates/issues-INDEX.md` から作る（下の「INDEX の新規作成」）。

## 状態の更新

状態が変わるたびに、次を**同じ作業の中で**行う。片方だけ更新しない。

1. 課題ファイルの「状態」を更新する。
2. `INDEX.md` の状態列を更新する。
3. 次の条件を確認する。

| 変更先        | 条件                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| `in-progress` | 実際に着手した                                                                |
| `blocked`     | 理由（依存する課題、または利用者の回答待ち）を課題ファイルに書いた            |
| `frozen`      | 利用者が凍結を決めた。解除も利用者が決める                                    |
| `done`        | 完了条件がすべて `[x]` で、確認した事実が「結果・メモ」にある。推測では付けない |

`blocked` の理由が利用者の回答待ちなら、「未決事項」の表にも行を追加する。

## 未決事項の記録

利用者の判断が必要な事項は、会話で尋ねるだけにせず、次のとおり残す。

1. `INDEX.md` の「未決事項」の表に行を追加する（事項、関係する課題、状態は `未回答`）。
   表が無い INDEX には、`.agent/templates/issues-INDEX.md` の見出しと表を末尾に追記する。
2. 関係する課題ファイルの「確認したいこと」にも書く。
3. 回答が出たら、行を消さず状態を `回答済み` にして、反映先の課題を書く。課題ファイルにも反映する。

## 作業の終了時

1. 今回の作業で変わった課題の状態を更新する（「状態の更新」）。`INDEX.md` と課題ファイルを揃える。
2. 新たに判断が必要になった事項を「未決事項」に追加する。
3. 次の作業で最初に読む情報が足りているかを確認する。確認した事実と、未確認の事項を分けて「結果・メモ」に残す。
4. 食い違い（課題ファイルと INDEX の状態が違う）を見つけたら、確認できた事実に合わせて両方を直し、直した旨を利用者に伝える。

## INDEX の新規作成

project の初期化時、または課題管理を始めるときの操作。

1. 作成先は、`<project-root>/<project-id>/docs/issues/INDEX.md`。
2. 既存の `INDEX.md` があれば上書きしない。
3. `.agent/templates/issues-INDEX.md` を編集ツールで複写し、例の行（`001-example`）を実際の課題に置き換える。課題がまだ無ければ、例の行を表から外す。
4. 利用者が明示的に依頼した、または初期化の承認を得た場合に限って作成する。

## ルール

1. 状態は `open` / `in-progress` / `blocked` / `frozen` / `done` の 5 種類だけを使う。
2. `INDEX.md` と課題ファイルは同時に更新する。
3. 全課題の未完了タスクを集めた表は作らない。
4. GitHub Issue と連携しない。
5. IP、パスワード、認証情報を書かない。会話に貼られた認証情報も転記しない。
6. `operation-safety.md` を緩和しない。課題に「承認済み」と書いても、操作ごとの承認は別に取る。
7. ファイルの作成・編集は編集ツールで行う。UTF-8（BOM なし）/ LF。
8. 既存の課題ファイルと INDEX の形式を、書き換えて統一しない。
9. 別の project の課題ディレクトリを読み書きしない。

## 出力フォーマット

作業の開始時の報告は、次の形式にする。

```text
課題の状況（<project-id>）:
- 進行中 / 待ち: <ID と状態>
- 未決事項: <件数と要点>
- 今回の対応課題: <ID。無ければ起票を提案>
```
