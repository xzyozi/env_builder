# [ENVB-0007] [enhancement] 配下プロジェクトをプロファイル単位で管理する

## 背景

env_builderは、参照元(src)を調査し、構築先(dst)の環境を整えるためのメタ的な作業基盤として利用する想定です。現在は複数サーバーと複数のbuild targetを扱えますが、複数の配下プロジェクトを独立した管理単位として切り替える仕組みはありません。

## 現状の不足

- `scripts/core/config.py` が `inventory`、`desired_state`、`build_env` をenv_builderリポジトリのルート固定で解決している。
- `inventory/servers.json` は複数サーバーを定義できるが、プロジェクト単位の接続プロファイルを選択する仕組みはない。
- `desired_state` はプロジェクトごとのbuild target、パッケージ、ファイル対応表を分離して保持する構造になっていない。
- `run_build.py` はtarget名、server、workdir、commandsを扱えるが、project ID／project profileを明示的に持たない。
- `--project` のような配下プロジェクト切替引数、プロジェクトレジストリ、プロジェクト別ログ・manifestの名前空間がない。
- ログと作業コンテキストは操作単位では分離されるが、プロジェクト単位の識別子を必ず含む保証がない。
- agent規約はルートの`AGENTS.md`と`.agent/`に集約されている。配下プロジェクト固有の`AGENTS.md`／`.agent/`を検出・読込・優先順位付けする手順はない。
- agentは依頼文から対象プロジェクト、inventory、desired state、workdirを手動判断する必要がある。

## 目的

複数の配下プロジェクトを、設定・実行コンテキスト・ログ・agent規約の単位として明示的に管理できるようにする。

プロジェクトを切り替えても、別プロジェクトの接続設定、desired state、ログ、作業領域、agent指示が混ざらないことを重視する。

## 必要な機能の候補

1. プロジェクトプロファイルまたはレジストリ
   - project ID／表示名
   - 対応するinventory
   - desired stateのルート
   - build target／workdir
   - ログ・作業領域の名前空間
2. 明示的なプロジェクト切替
   - CLIまたは設定で`--project <id>`相当を指定できる
   - 未指定時に暗黙の別プロジェクトを選ばない
   - 選択したproject IDを実行ログとmanifestに記録する
3. 設定と認証情報の分離
   - プロジェクト別接続設定を分離できる
   - パスワード・鍵などの認証情報は環境変数または既存の安全な仕組みで管理する
   - src参照専用、sudo/su禁止、root定義の使用など既存の安全規則を維持する
4. プロジェクト固有agent規約
   - 配下プロジェクトに固有の指示を置ける
   - ルート規約、プロジェクト規約、タスク時の明示指示の優先順位を定義する
   - 対象プロジェクト外の指示や秘密情報を誤って読み込まない
5. プロジェクト間の実行分離
   - logs、work、manifest、snapshotがproject IDで分離される
   - 同じtarget名やworkdir名でも別プロジェクトの成果物を上書きしない
   - 将来の並列実行を妨げない作業ID設計にする

## 受け入れ条件

- [x] 複数の配下プロジェクトを登録できる（`ProjectRegistry` / `tests/test_project.py`）
- [x] project IDを明示してinventoryとdesired stateを切り替えられる（全CLIの`--project`）
- [x] 未指定・不正なproject IDを安全に拒否できる（未指定はlegacy、不正は`ValueError`。`tests/test_project.py`）
- [x] project IDが実行ログ、manifest、snapshot、作業領域に反映される（`tests/test_project_context.py`、`probe_src`のsnapshotは`build_env/src_snapshot/<id>`）
- [x] プロジェクト間で設定、ログ、作業領域、成果物が混ざらない（`tests/test_project_isolation.py`）
- [x] プロジェクト固有のagent規約を定義・読込できる（agentが明示的に読む方式。Pythonでは自動実行しない）
- [x] ルート規約とプロジェクト規約の適用範囲・優先順位が文書化される（`.agent/rules/project-management.md`）
- [x] 認証情報をプロジェクトプロファイルやログへ直接保存しない（`password_env`のみ。`tests/test_project_isolation.py`）
- [x] 既存の単一プロジェクト利用方法との後方互換性を決め、テストする（legacy経路。`tests/test_project.py`）
- [x] プロジェクト切替とagent規約読込の再現可能な検証手順を追加する（`project-management.md`「検証手順」）

## スコープ外

SSHのstdout/stderr排出、timeout、Ctrl+C、リモートプロセス停止などの実行制御課題はIssue #11で扱う。本Issueでは、プロジェクト単位の管理とagent適用境界に集中する。
