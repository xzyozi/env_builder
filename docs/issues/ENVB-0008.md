# [ENVB-0008] [design] scripts をパッケージ化し、CLI・共通基盤・処理本体を分離する

## 背景

`scripts/` 直下に8つのCLIが並んでおり、コンテナ関連の機能（別Issue）を追加するとさらに増える。現在の構成には次の問題がある。

- **import経路が2系統ある。** CLIは `sys.path.insert(0, scripts/)` のあと `core.*` を読み、テストは `scripts.core.*` を読む。pytest の経路では同じファイルが別モジュールとして二重にロードされる（`core.project.ProjectRegistry is scripts.core.project.ProjectRegistry` が `False` になることを確認済み）。monkeypatch や isinstance が片側にしか効かない。
- **CLIとcoreの間で型検査が効いていない。** 設定なしで mypy を実行すると、CLIの `from core.xxx import ...` は `import-not-found` になる。現在は設定でこのエラーを無視しているため、CLIとcoreの間は型チェックされていません。
- **定型処理が重複している。** 8本すべてが `sys.path.insert` と `# noqa: E402` を持つ。`--project` の定義（help文まで同じ）と、`ProjectRegistry().resolve` → `get_logger` → `load_inventory` の準備処理が各CLIにある（5本は同じ記述）。
- **CLIにCLI以外の処理が混在している。** desired_state の読込、導入済み判定、ビルド失敗マーカーの判定、転送パイプラインがCLIの中にある。テストはCLIのprivate関数（`_load_packages` / `_load_targets` / `_load_files`）を直接importしている。
- **文書が実装とずれている。** READMEの構成図に `core/project.py` が無い。`core` の責務がREADME（5項目）と `coding-style.md`（3項目）で異なる。`coding-style.md` は `sys.path` を足す作法を規約にしている。

## 参考: ansible/ansible

- [`lib/ansible/`](https://github.com/ansible/ansible/tree/devel/lib/ansible) を `cli/`（コマンドの入口）、`modules/`（対象ホストで動く処理）、`module_utils/`（共有コード）、`plugins/connection/`（local / ssh / psrp / winrm）、`inventory/`、`executor/` などに分けている。
- コマンドは [`pyproject.toml`](https://github.com/ansible/ansible/blob/devel/pyproject.toml) の `[project.scripts]` で `ansible-playbook = "ansible.cli.playbook:main"` のように `cli` の `main` を指すだけの薄い入口になっている。
- 取り入れる点: 薄いCLI層・処理本体・共通基盤の分離。パッケージ名から始まる1系統のimport。
- 取り入れない点: プラグインローダー、collection、playbook実行エンジン。現在の規模には過剰なため。
- ansible-core は GPL-3.0-or-later、本リポジトリは MIT のため、コードは流用せず構成の考え方だけを参考にする。

## 方針（提案）

### 構成

```text
env_builder/                    # import は env_builder.* の1系統だけ
├── __init__.py
├── __main__.py                 # uv run python -m env_builder <command>
├── cli/                        # 引数解析・表示・終了コードだけ（1コマンド1ファイル）
│   ├── __init__.py             # コマンド名と main の対応表
│   ├── _common.py              # --project 等の共通引数、profile・logger・inventory の準備
│   ├── init_config.py
│   ├── check_connectivity.py
│   ├── probe_src.py
│   ├── remote_exec.py
│   ├── run_build.py
│   ├── apply_packages.py
│   ├── sync_files.py
│   └── sync_tree.py
├── core/                       # 現 scripts/core（責務は変えない）
│   ├── __init__.py
│   ├── config.py
│   ├── desired_state.py        # 新規: desired_state の JSON 解決・読込
│   ├── logging_utils.py
│   ├── project.py
│   ├── ssh.py
│   └── work_context.py
└── ops/                        # CLI から切り出す機械的処理（判断は持たない）
    ├── __init__.py
    ├── build.py                # ビルド手順の実行・失敗マーカー判定
    ├── packages.py             # 導入済み判定・導入コマンドの組み立て
    └── transfer.py             # files / tree の中継転送
scripts/                        # 移行期間の互換ラッパーだけ
└── <name>.py                   # env_builder.cli.<name>.main を呼ぶ
```

- 処理本体が小さいCLI（`init_config` / `check_connectivity` / `probe_src` / `remote_exec`）には `ops/` を作らず、`cli/` から `core` を直接使う。中身の無い層は作らない。
- コンテナ機能（別Issue）は `ops/container/` と `cli/` へのファイル追加で収まる。
- `core/config.py` の `REPO_ROOT = Path(__file__).resolve().parents[2]` は移設後も同じ階層を指すため、変更不要。

### 実行形式

- 新しい形式: `uv run python -m env_builder <command> ...`
  - 例: `uv run python -m env_builder remote-exec --target dst -- "hostname"`
- `uv run python scripts/<name>.py ...` は互換ラッパーで当面動かす。引数・既定値・終了コード・ログの出力先は変えない。
- `[project.scripts]` によるコマンド化は見送る。`REPO_ROOT` をコードの位置から求めているため、通常のインストールでは `inventory/` などの解決先が変わる。`[tool.uv] package = false` を維持し、リポジトリ直下で実行する前提を変えない。

### テストの境界（seam）

- 3つの desired_state 読込関数を `core/desired_state.py` の公開関数にまとめる。ファイル名の候補、後方互換の探索順、エラー文言は維持する。テストは公開関数を対象にする。
- `ops/` の関数は接続を内部で作らず、`run()` / `get_file()` / `put_file()` を持つセッションを引数で受け取る。本番は `SSHSession`、テストは記録済みの結果を返す fake を渡す。SSH無しで導入済み判定・失敗マーカー判定・cleanup経路を検証できる。

## 対象範囲

PRは2段階に分ける。

### Step 1: 移設（挙動は変えない）

1. `scripts/core` を `env_builder/core` へ、8つのCLIを `env_builder/cli/` へ移す。importを `env_builder.*` に揃え、`sys.path.insert` と `# noqa: E402` を削除する。`scripts/__init__.py` は削除する。
2. `env_builder/__main__.py` にコマンドの対応表を置く。各 `main()` は `argv` を引数で受け取れるようにする。
3. `cli/_common.py` に共通引数と準備処理をまとめる。
4. `scripts/<name>.py` を互換ラッパーにする。`sys.path` を操作するのはここだけにする。
5. mypy の検査対象を `files` で明示する（Git管理外の `tmp/` などを拾わない）。`ignore_missing_imports` は paramiko だけに限定する。
6. README、`.agent/`（rules / references / skills）、`.kiro/agents/project-initializer.md`、`pyproject.toml` のコメントを新構成に合わせる。調査時点で `scripts/<name>.py` 形式のパス参照は18ファイル・51行ある。

### Step 2: 処理本体の切り出し

7. `core/desired_state.py` を追加し、テストをprivate関数から公開関数へ切り替える。
8. `ops/build.py` / `ops/packages.py` / `ops/transfer.py` へ処理を移し、セッションを引数で受け取る形にする。
9. fake セッションを使ったテストを追加する。

## 決定事項

Step 1 で採用:

- パッケージ名: `env_builder`（pyproject の name と同じ）。
- コマンド名: ファイル名と同じ `remote_exec`（snake_case）を正とし、`remote-exec` も受け付ける。
- 処理本体の置き場所の名前: `ops/`（既存の `ops/container.py` を維持）。

Step 2 で採用:

- `core/desired_state.py`: `load_packages` / `load_files` / `load_build_targets`。読み込み順・後方互換の fallback・エラー文言は維持。
- `ops/session.py`: 受け取るセッションの型。`CommandRunner` は `WorkContext` など core からも使うため `core/ssh.py` に置き、ops から再公開する（core が ops に依存する逆向きの依存を避ける）。
- `ops/packages.py` / `ops/build.py` / `ops/transfer.py`: 接続を内部で作らず、セッションを引数で受け取る。失敗は例外ではなく戻り値で返す。
- `sync_files` は入力の対応表を書き換えず（`_local` を足さず）、取得先パスのリストを返す形にした。

  `main()` の結合は未追加。
