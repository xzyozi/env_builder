# [ENVB-0009] [enhancement] Podman/Docker共通のimage取得・移送とコンテナ起動仕様解析を追加する

## 目的

現在のコンテナを参照して、別環境で同じengineのコンテナ環境を再構成できるようにする。

対象は次の2つを一連の機能として扱う。

1. 移行先にimageがない場合のimage取得・移送
2. 現在のコンテナの設定を解析し、`podman run` / `docker run`候補を提示すること

元の手入力コマンドを完全に復元する機能ではなく、現在のコンテナ状態から再現候補と不足事項を提示する機能とする。

## 壁打ちで確定した要件

### プロジェクトとimage

- 使用するコンテナimageは、プロジェクト作成前に決定する。
- プロジェクト設定をimageの使用元とし、imageを暗黙に選択しない。
- プロジェクト設定には、少なくとも次を定義する。
  - engine（PodmanまたはDocker）
  - image
  - 移送元のinventory target
  - 移送先のinventory target
  - 参照するコンテナ名またはID
- コンテナIDは変わる可能性があるため、名前を基本とし、IDは一致確認に使う。
- 基本経路は`src`から`dst`だが、移送元・移送先はinventoryの任意targetとして扱える構成にする。

### 対応engine

初期対応は同一engine間に限定する。

- Podman → Podman
- Docker → Docker

DockerとPodmanの相互変換は初期対象外とする。engine固有差分はadapterへ閉じ込め、将来要件が発生した場合に追加する。

### imageの取得・移送

通常方式と高再現性方式を分ける。

#### 通常方式

- 移送元では`podman export` / `docker export`
- 移送先では`podman import` / `docker import`
- 移送元のimage storeを変更しない
- filesystemを移送し、inspect結果から起動に必要なimage設定を補う

#### 高再現性方式

必要な場合だけ、実行計画への明示承認後に使用する。

- Podman: `podman commit` → `podman save/load`
- Docker: `docker commit` → `docker save/load`
- 元imageのレイヤ・履歴・tagを保持しやすい
- `commit`は移送元のimage storeを変更するため、通常方式より強い承認が必要

元imageが移行先にない場合、または移送元で元imageが失われている場合は、現在のコンテナから派生imageを作成できる方式を用意する。ただし、元imageの履歴、親子関係、Dockerfile/Containerfileの完全復元は保証しない。

`bind mount`、named volume、secret/config、device/GPU、networkはimageには含めない。

### imageのtag

- 日付と時刻を含むtagを作成する。
- UTCで統一する。
- 例: `<project-id>:20261006-153000`
- image digestをJSONへ記録する。
- 既存imageの上書きは行わない。
- 同名tagが存在する場合は安全側で停止し、既存imageを削除しない。

### 外部依存の扱い

- bind mountの通常ファイル・ディレクトリは、既存の`sync_files` / `sync_tree`で扱う。
- desired stateに明示されていないファイルは自動取得しない。
- named volume、secret、device、GPU、networkは自動移送しない。
- portとrestart policyはrun候補へ反映する。
- 移送できない外部依存は警告・要確認事項として出力する。

### run候補の対応範囲

初期実装では、基本的な環境構築に必要な項目を対応する。

- image
- container name
- command / entrypoint
- environment
- working directory
- user
- port
- bind mount
- network
- restart policy

次の高度な項目は解析対象として収集するが、初期実装ではrun候補への反映を保証しない。

- resource制限
- capability
- security option
- device/GPU
- ulimit
- namespace
- healthcheck
- loggingなど

未対応項目は「設定がない」と混同せず、未対応または要確認として明示する。

### 出力

次の3つを出力する。

1. 人間向けの`podman run` / `docker run`候補
2. 機械可読な解析結果JSON
3. image取得・移送を含む実行計画

実行計画の状態は次のように管理する。

- 解析済み
- 承認待ち
- 実行済み
- 警告
- 未対応

run引数は内部では構造化データまたはargvとして保持し、inspectの値をshell文字列へ直接連結しない。表示時だけ安全にquoteする。

### 秘密情報

- inspect結果の秘密値は取得・保存しない。
- 環境変数は実値ではなく、プロジェクトで定義した環境変数参照へ置き換える。
- 例: `${ENVB_CONTAINER_PASSWORD}`
- JSON、ログ、run候補、実行コマンドへpassword/token等の実値を出さない。
- secret/configの内容自体は初期対象外とする。

### rootless / rootful

- 基本は移送元と移送先で同じ実行コンテキストを使用する。
- rootless / rootfulが異なる場合は、UID/GID mapping、所有権、port、volume、device等の差異を解析する。
- 対応可能な差異だけ、明示承認後に進める。
- sudo / suによる自動昇格は行わない。
- `dst`と`dst_root`を暗黙に切り替えない。

### 承認と実行

- image取得・移送はひとつの実行計画として承認する。
- 承認後にexport/importまたはcommit/save/loadを実行する。
- runは自動実行しない。
- 移送後にrun候補を表示し、ユーザーが確認して手動実行する。

### 失敗時・再実行時

- 専用作業領域とarchiveは成功・失敗を問わずcleanupする。
- 作成済みimageは自動削除しない。
- 作成したimageのID、digest、状態をmanifestへ記録する。
- 再実行時は既存digestを確認し、同じimageを再利用できるようにする。
- rollback目的で既存imageやcontainerを自動削除しない。
- cleanup失敗もmanifestへ記録する。
- 途中で生成されたimageは、ユーザーが確認して不要な場合に別途削除する。

## 実装方針

Issue #15「scriptsをパッケージ化し、CLI・共通基盤・処理本体を分離する」の完了後、または移設後の構成を前提に実装する。

想定配置:

```text
env_builder/
├── cli/
│   └── container.py
├── core/
│   └── container/
│       ├── model.py
│       ├── inspect.py
│       ├── command.py
│       └── engines/
│           ├── base.py
│           ├── docker.py
│           └── podman.py
└── ops/
    └── container/
        ├── inspect.py
        ├── image.py
        └── run_spec.py
```

- `SSHSession`、`ProjectProfile`、`WorkContext`を再利用する。
- Docker/Podman固有のCLI差分はengine adapterに閉じ込める。
- 共通モデルへ正規化した後にrun候補を生成する。
- image archiveは`build_env/work/<work-id>/`とリモートの専用`/tmp/env_builder-<work-id>-XXXXXX/`だけで扱い、Gitへ保存しない。
- Ansibleの構成分離と、[docker_util.py](https://github.com/ansible/ansible/blob/devel/test/lib/ansible_test/_internal/docker_util.py)のDocker/Podman共通化を参考にする。コードは流用しない。

## 対象外

- DockerとPodman間の相互変換
- 元の手入力コマンドの完全復元
- 元imageのDockerfile/Containerfileの逆生成
- bind mount、named volume、secret、device、GPUの自動移送
- ContainerfileやQuadletの生成
- runの無確認な自動実行
- 無確認のstop、rm、prune、既存imageの上書き
- Ansible本体または`containers.podman` collectionへの依存追加
