# [ENVB-0010] [security] apply_packages / run_build における引数展開起因のシェルコマンドインジェクション

## 0. メタ情報 (Scope & Impact)
- **影響範囲**: 本番影響あり（要レビュー）。リモートへ渡すコマンド文字列の組み立てが変わる。
- **既存コードへの依存**: あり（`apply_packages.py` / `run_build.py` の既存関数を変更）
- **関連Issue**: #1（`sync_tree.py` の同種の問題）の後続。GitHub Issue は未起票（`issue:pending`）。

## 1. 概要・背景
`desired_state` の値と設定ファイル由来の文字列が、エスケープされないままリモートシェルのコマンド文字列に埋め込まれている。#1 で `sync_tree.py` は修正済みだが、同じ種類の問題が次の箇所に残っている。

- `scripts/apply_packages.py`: `rpm -q {pkg}` と `{pm} install -y <packages>` にパッケージ名とパッケージマネージャ名を直接展開している。dst は root ログイン前提のため、細工された名前は root 権限で実行される。
- `scripts/run_build.py`: `export {k}={v};` に環境変数名と値を、`cd {workdir}` に作業ディレクトリを直接展開している。

`desired_state` は Git 管理外のローカル設定だが、別プロジェクトから取り込んだ定義や、貼り付けた定義に意図しないメタ文字が混ざる事故を防ぐため、入口で安全に扱う。

## 2. 仕様および要求事項 (修正方針の検討)
- [x] **案 1 (推奨): クォートと入力検証の併用**
  - 方針概要: リモートへ渡す値は `shlex.quote` でリテラルとして扱う。名前系（パッケージ名、パッケージマネージャ名、環境変数名）は許可文字で事前検証し、違反時は実行前に停止する。`workdir` の先頭 `~` はホームディレクトリとして扱えるよう `"$HOME"` に置き換える。
  - メリット: 既存の実行フローを変えずに、インジェクションと意図しない展開を防げる。
  - 留意点: `env` の値はリテラル扱いになり、シェル展開（`$HOME` 等）には使えなくなる。`commands` は設計上シェルコマンドそのものなので、クォート対象外とする。
- [ ] **案 2**: `env` の値でもシェル展開を許可し、検証だけ行う。
  - 不採用理由: 展開を許すと検証でメタ文字を弾けず、インジェクションを防げない。

## 3. 段階的実装手順 (Step-by-step Execution)
- **Phase 1 (Core Implementation)**: `scripts/core/shell.py` に `quote_remote_path` / `validate_package_name` / `validate_env_name` を追加する。`apply_packages.py` と `run_build.py` のコマンド組み立てを純粋関数に切り出し、上記を適用する。
- **Phase 2 (Test Implementation & Refinement)**: メタ文字（`;`、`$()`、バッククォート、改行、空白）を含む入力で、1つの引数のまま扱われること、不正な名前が実行前に拒否されることをテストする。

## 4. 編集対象ファイル (Target Files)

- `scripts/apply_packages.py`
- `scripts/run_build.py`
- `tests/test_shell_quoting.py`（新規）

## 5. ドメイン知識・技術上の落とし穴 (Domain Knowledge & Technical Pitfalls)
- `shlex.quote` は `~` を展開させない。`workdir` が `~/` で始まる場合は `"$HOME"` に置き換えて、残りをクォートする。
- 現行の `desired_state/build_targets.local.json` の `env` 値と `workdir` は、シェル展開も空白も含まないことを確認済み。リテラル化で挙動は変わらない。
- `rpm -q` のパッケージ名は、`rpm -q -- <name>` のように `--` を挟んでオプション誤認を防ぐ。`dnf install` は `--` の扱いが版により異なるため、先頭が `-` の名前は検証で拒否する。
- **検証用データ・環境の準備方針**: SSH 接続は不要。コマンド文字列を生成する純粋関数を `shlex.split` で分解して検証する。

## 6. 設計制約・アンチパターンの禁止 (Architecture Constraints & Forbidden Actions)
- 単一責任と一方向のデータフローを維持すること。
- `commands`（ビルド手順そのもの）をクォートして壊さないこと。
- 既存の公開 API シグネチャや、`desired_state` の既存スキーマを破壊しないこと。

## 7. 対象外 (Non-Goals)
- `commands` の内容検証。
- パッケージ導入の判定を `rpm` 以外に切り替えること。
- 大規模なリファクタリング（#15 で扱う）。
